## 1. 阅读指南

### 1.1 目的

将日本 SIer 标准的 150 任务工程工作流完整映射到 CATs 项目，作为：

- **项目执行的参考骨架**：覆盖从超上流到终结的全生命周期
- **评审会的进度快照**：当前 42 已完成 / 33 进行中 / 75 未启动（28%）
- **责任与分工的基线**：RACI 矩阵（PM / 架构师 / BA / 开发者 / QA / SRE / DBA / 客户）
- **阻塞项的权威清单**：12 项 P0 关心事项必须在 M1 启动前 Closed

### 1.2 范围

| 维度 | 范围 |
|------|------|
| **适用项目** | CATs（AI 增强型 CAT 浏览器工作台） |
| **适用阶段** | 全生命周期（超上流 → 終結） |
| **任务粒度** | 150 任务（16 フェーズ） |
| **时间窗口** | 2026-08 ~ 2027-12（M1 ~ M3 实际开发与上线） |
| **不适用** | 探索性 PoC（仅参考，不强制套用） |

### 1.3 读者

- **PM / PMO**：用于项目跟踪、评审会准备
- **架构师 / BA / 开发者 / QA / SRE / DBA**：了解本职责任与上下游接口
- **客户 / 业务方**：了解项目阶段与交付物
- **新入组成员**：快速建立全局认知

### 1.4 术语

| 术语 | 含义 |
|------|------|
| **フェーズ** | 工程阶段（中文：阶段） |
| **略称** | 业界常用缩写（如 UR/BR/SR/FR/NFR/SA/API/IF/DB/ER/UT/IT/ST/PT/UAT/CM/CR） |
| **RACI** | Responsible / Accountable / Consulted / Informed 责任分配模型 |
| **V 字模型** | 左侧开发阶段（超上流→要件→基本→详细→実装）↔ 右侧测试阶段（受入→ST→IT→UT） |
| **P0 阻塞项** | 必须在 M1 启动前关闭的关键决策（指向 QA 登记册） |

### 1.5 状态图例

| 符号 | 状态 | 含义 |
|------|------|------|
| ✅ | 已完成 | 任务已通过评审/批准 |
| 🟡 | 进行中 | 任务正在进行（有产出物） |
| ⚪ | 未启动 | 任务尚未启动 |
| 🔴 | 阻塞 | 任务因外部依赖被阻塞 |

## 3. フェーズ詳細

> 本节对 16 フェーズ进行简要说明；与 §2 表 + §4 CATs 状态快照 + §6 阻塞项组合阅读。

### 3.1 超上流（01-09）

**目标**：从业务经营层出发，确认系统化的必要性与可行性，完成项目立项。

- 关键产出：经营要求确认书、系统化构想书、立项决议、As-Is/To-Be 流程图
- 评审点：立项决议会（取締役会 / 経営層）
- 风险：经营层认知差异、立项后范围蔓延

### 3.2 要件定義（10-21）

**目标**：将业务诉求转为可验收的需求规格（FR/NFR/IF/Sec），并完成基线化。

- 关键产出：UR/BR/SR/FR/NFR/数据/IF/安全/运行/迁移 各类要件定义书 + 评审 + 基线
- 评审点：要件レビュー（RD Review） + 要件承認
- 风险：客户与开发方对"必须/应该/可以"理解不一致

### 3.3 基本設計（22-41）

**目标**：完成系统级架构、模块划分、接口契约、数据模型、基础设施、运维方式等基线设计。

- 关键产出：架构设计书、API 设计书、DB 设计书、UI 设计、权限/安全/网络/备份/迁移设计
- 评审点：基本设计评审（BD Review）
- 风险：架构决策在后期发现不可行（需架构变更管理）

### 3.4 詳細設計（42-52）

**目标**：将基本设计细化为程序级（类/方法/SQL/批处理/错误/日志）。

- 关键产出：模块详细设计、API 详细契约、SQL 清单、错误码表、日志设计
- 评审点：详细设计评审（DD Review）
- 风险：详细设计与基本设计偏离、SQL 性能未考虑

### 3.5 実装（53-58）

**目标**：按详细设计实现代码，并通过 CI/CR/SAST 等质量门禁。

- 关键产出：源代码、CI Pipeline、SAST 报告
- 评审点：代码评审（CR）+ CI 绿灯
- 风险：未遵守代码规范、未写单元测试、提交含 secret

### 3.6 単体試験（59-65）

**目标**：验证各模块/函数级别的正确性（含单元测试 + SAST）。

- 关键产出：UT 计划、UT 用例、UT 执行报告
- 评审点：UT 评审、UT 完成批准
- 风险：覆盖率不足、只测 happy path

### 3.7 結合試験（66-75）

**目标**：验证服务内/服务间/API/DB/外部系统集成正确性。

- 关键产出：IT 计划、IT 用例、IT 报告、回归测试报告
- 评审点：IT 完成判定
- 风险：环境与生产差异、Mock 偏差

### 3.8 システム試験（76-89）

**目标**：端到端验证功能、性能、负载、压力、安全、可靠性、可用性、运维流程。

- 关键产出：ST 计划、ST 用例、性能/负载/压力/安全测试报告、ST 完成批准
- 评审点：ST 评审、ST 完成批准
- 风险：性能基线不达标、灾备流程不实战化

### 3.9 受入試験（90-95）

**目标**：由用户/客户主导的验收测试与正式验收。

- 关键产出：UAT 计划、UAT 用例、UAT 报告、受入判定、検収书
- 评审点：受入判定会、検収签字
- 风险：客户期望管理不当、UAT 环境不足

### 3.10 移行（96-101）

**目标**：按计划将系统切换至生产环境（含数据迁移、系统切换、结果确认）。

- 关键产出：迁移计划、迁移步骤、迁移预演记录、数据迁移报告
- 评审点：迁移前 Go/No-Go
- 风险：数据丢失、切换时间窗超期、回滚失败

### 3.11 リリース（102-108）

**目标**：完成发布计划、评审、生产环境构建、Canary 部署、冒烟、上线、Hypercare。

- 关键产出：发布计划、Go/No-Go 决议、生产构建、Canary 监控、Smoke 报告
- 评审点：发布评审会
- 风险：Canary 流量切分失败、回滚预案不足

### 3.12 運用（109-117）

**目标**：日常运维（监控、作业、备份、容量、事件、故障、问题、咨询）。

- 关键产出：运维手册、监控告警台、备份验证记录、值班表
- 评审点：月度运维评审
- 风险：监控盲区、值班交接不顺畅

### 3.13 保守（118-126）

**目标**：响应变更请求、影响分析、变更审批、配置管理、补丁/漏洞/改进/紧急修复/回归。

- 关键产出：CR 登记册、影响分析报告、变更工单、回归测试报告
- 评审点：变更评审会（CAB）
- 风险：紧急变更绕过流程、回归不充分

### 3.14 品質管理（127-130）

**目标**：贯穿全生命周期的 QA 计划、评审、评估、审计。

- 关键产出：QA 计划、QA 评审记录、质量评估报告、第三方审计报告
- 评审点：QA 月度评审、年度审计
- 风险：QA 流于形式、与业务脱节

### 3.15 管理（131-144）

**目标**：项目级管理（计划/WBS/进度/课题/风险/变更/配置/成果物/评审/会议/工数/成本/范围/基线）。

- 关键产出：项目计划、WBS、进度报告、课题登记册、风险登记册、变更决议、配置台账
- 评审点：月度ステコミ、周次進捗会議
- 风险：风险应对滞后、范围蔓延、基线管理失序

### 3.16 終結（145-150）

**目标**：项目完成判定、交付物移交、报告、复盘、知识转移、归档。

- 关键产出：完成判定书、移交清单、结项报告、复盘纪要、KT 记录、归档清单
- 评审点：终结会
- 风险：经验未沉淀、文档缺失
