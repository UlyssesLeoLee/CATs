## 1. QA-018 审计日志保留期

### 1.1 背景

CATs 多租户 SaaS 在不同客户层（free / pro / enterprise）下，审计日志的合规要求差异极大：基础客户 365 天足够（GDPR 默认），企业客户（金融/医疗/政府）则要求 7 年（等保 2.0 三级、HIPAA、SOX 等）。统一策略无法满足两端。

### 1.2 关心事项

QA 登记册 v1.1 §2.3：审计日志保留期 Open（合规决定 365d/7y/配置化未敲定）。

### 1.3 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| A. 365d 统一 | 全平台统一 365 天 | 简单、运维成本低 | enterprise 客户合规风险 |
| B. 7y 统一 | 全平台 7 年 | 合规兜底 | 存储成本爆炸（7y × 14 服务 × 50万句段/日 ≈ 数 PB） |
| C. **配置化（默认 365d）** ✅ | tenant 级配置，默认 365d，enterprise 可签 7y | 兼顾合规 + 成本 | 需要 schema/迁移/UI 三处改造 |

### 1.4 决策

**采用 C：配置化策略，默认 365 天，enterprise tier 签约时可配置 365~2555 天**。

实施细则：

1. **schema 层**：`admin.tenant_config` 表新增字段 `audit_retention_days INT DEFAULT 365, CHECK (audit_retention_days BETWEEN 365 AND 2555)`
2. **数据层**：ETL 批处理 L-5 改造为按 tenant 配置分批归档/删除；归档数据落到 S3 冷存储
3. **UI 层**：admin UI "租户设置" 页面新增"审计保留期"配置项（仅 super-admin 可见/可改）
4. **API 层**：`PUT /admin/tenants/:id/audit-retention` 端点 + 审计触发（"谁改了什么"）
5. **签约 SOW**：enterprise tier SOW 模板新增"审计保留期"条款，默认 2555 天

### 1.5 影响

- **正面**：合规兜底（满足 enterprise 客户）、存储成本可控（默认 365d）
- **负面**：schema 改造 + ETL 改造 + UI 改造需 M1-Sprint 1 工作量约 4-6 人日
- **风险**：租户误改配置导致日志被提前归档 → 写入前必须经 super-admin 二次确认

### 1.6 验证 / 关闭

- 关闭时点：M1-Sprint 1 末
- 验证动作：admin 服务 + ETL 服务灰度部署 + enterprise 客户签约 SOW 模板更新
- 签字方：合规 + DBA

### 1.7 关联

- 上游：QA 登记册 v1.1 §2.3
- 关联 ADR：ADR-001（多租户隔离）、ADR-005（认证 + 多租户）
- 下游：`CATs_数据库设计书_v2.0` §4（admin.tenant_config 表）、`CATs_批处理详细设计_v1.0` §ETL、`CATs_运用マニュアル_v1.0` §备份

## 2. QA-043 延迟 SLO 数值

### 2.1 背景

测试设计书 §4.5 已标注延迟 SLO（L0<100ms / L2<1s / L3<5s）为"初版，待 PRE 校准"。这些数值未经过 300 万句段基线压测，存在两类风险：① 数值过松导致性能预算失控；② 数值过严导致 M1 启动即失败。

### 2.2 关心事项

QA 登记册 v1.1 §2.3：延迟 SLO 数值 Open（M1 实测校准）。

### 2.3 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| A. 沿用初版 | 维持 L0<100ms / L2<1s | 简单，立即可用 | 未实测，存在不达标风险 |
| B. 立即压测定 | M1-Sprint 0 启动前压测 | 数据扎实 | 阻塞 M1 启动 |
| C. **初版 + M1-S1 末校准** ✅ | 初版作为内部目标，M1-S1 末 benchmark 跑完校准为正式 SLO | 兼顾启动速度 + 数据驱动 | 需要双轨维护 |

### 2.4 决策

**采用 C：双轨 SLO**。

**SLO v0.9（初版，M1-Sprint 0-1 内部目标）**：

| 路径 | 目标 P99 |
|------|---------|
| L0 实时翻译接口 | < 100ms |
| L1 TM 召回 | < 200ms |
| L2 短文档翻译（< 1k 句段） | < 1s |
| L3 长文档翻译（> 1k 句段） | < 5s |
| L4 协同 WebSocket 推送 | < 50ms |

**SLO v1.0（正式，M1-Sprint 1 末校准锁定）**：

- 校准依据：ADR-003 性能基线报告（300 万句段 + hnsw.ef_search=40）
- 校准阈值：实测 P99 × 1.2（留 20% 余量）作为正式 SLO
- 锁定时点：2026-09 末
- 锁定文件：测试设计书 §4.5 升 v1.1，ADR-003 升 v1.1

### 2.5 影响

- **正面**：M1 启动不被阻塞 + 1 个月内可获实测数据
- **负面**：双轨维护期间 SLO 不稳定，团队需要明确"内部目标 vs 对外承诺"
- **风险**：校准后 SLO 大幅放宽需对外解释 → 提前在 8-25 评审会披露

### 2.6 验证 / 关闭

- 关闭时点：M1-Sprint 1 末（2026-09 末 SLO v1.0 锁定）
- 验证动作：ADR-003 性能基线报告 + 测试设计书 §4.5 升 v1.1
- 签字方：测试 + 架构

### 2.7 关联

- 上游：QA 登记册 v1.1 §2.3
- 关联 ADR：ADR-003（数据存储选型，含性能基线）
- 下游：`CATs_测试设计书_v1.0` §4.5、`CATs_システムテスト報告_v1.0`（M2 末）

## 3. QA-045 feature flag 审批阈值

### 3.1 背景

可热插拔部署设计 §7.5 写"feature flag 影响范围 > 10% 需审批"，是 PMO 初步假设。实际项目应按 flag 风险等级分级审批：一刀切 10% 会让低风险 flag 过度流程化，5% 又会让 P0 flag 失控外溢。

### 3.2 关心事项

QA 登记册 v1.1 §2.3：feature flag 审批阈值 Open（运维策略调整）。

### 3.3 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| A. 10% 一刀切 | 影响 > 10% 一律 super-admin 审批 | 简单 | 低风险 flag 过度流程化 |
| B. 5% 全严 | 影响 > 5% 一律 super-admin 审批 | 保守 | 团队摩擦大 |
| C. **按风险等级分级** ✅ | P0 5% / P1 25% / P2 不审批 | 风险匹配 | 需 flag 风险分类机制 |

### 3.4 决策

**采用 C：按风险等级分级审批**。

| 风险等级 | 适用范围 | 审批阈值 | 审批人 |
|----------|----------|---------:|--------|
| **P0** | 影响核心路径（auth / billing / data mutation） | > 5% | super-admin |
| **P1** | 影响支撑路径（UI 改版 / 算法调优 / 性能优化） | > 25% | SRE Lead |
| **P2** | 实验性 / 文案 / 灰度 | 不审批 | flag owner 自决 |

实施细则：

1. **flag 元数据**：`feature_flags` 表新增 `risk_level ENUM('P0','P1','P2')` 字段
2. **CI 卡点**：`feature_flag_change` PR 必须标注 `risk_level`，否则 CI 拒收
3. **审批流**：admin UI 按 `risk_level` 路由到不同审批人
4. **审计**：所有 flag 变更写入 `audit_log`，包含 `risk_level / approver / rollout_pct`

### 3.5 影响

- **正面**：风险匹配审批成本，团队摩擦下降
- **负面**：flag owner 需要为每个 flag 评估风险等级 → 增加 flag 创建成本
- **风险**：P0 flag 误标 P1 绕过审批 → 灰度上线后由 SRE Lead 抽查 10% 复核

### 3.6 验证 / 关闭

- 关闭时点：M1-Sprint 1 末
- 验证动作：可热插拔部署设计书 §7.5 升 v1.1 + admin UI flag 审批流改造
- 签字方：运维 + SRE Lead

### 3.7 关联

- 上游：QA 登记册 v1.1 §2.3
- 关联 ADR：ADR-001（微服务架构）
- 下游：`CATs_可热插拔部署与运维设计_v1.0` §7.5、`CATs_开发运维_Guide_v1.0`

## 4. QA-046 Canary 阶段比例

### 4.1 背景

可热插拔部署设计 §8.2 写"Canary 5-25-50-100"，是行业常见但可调。CATs 15 服务按域分（核心/支撑/平台），风险程度不同：一刀切 5-25-50-100 对平台域过严，对核心域过松。

### 4.2 关心事项

QA 登记册 v1.1 §2.3：Canary 阶段比例 Open（运维策略调整）。

### 4.3 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| A. 5-25-50-100 统一 | 4 阶段统一 | 简单 | 不分域风险 |
| B. 1-10-50-100 统一 | 4 阶段更细 | 保守 | 部署时间翻倍 |
| C. **按服务等级分级** ✅ | 核心 5 阶段 / 支撑 4 阶段 / 平台 3 阶段 | 风险匹配 | 配置文件多 |

### 4.4 决策

**采用 C：按服务域分级 Canary**。

| 服务域 | 服务清单（ADR-001） | Canary 阶段 | 触发观察期 | 总部署时间 |
|--------|---------------------|-------------|-------------|------------|
| **核心域**（5 服务） | tm / term / llm-gateway / translate-orchestrator / qa-engine | 1% → 5% → 25% → 50% → 100% | 每阶段 30min | ~2.5h |
| **支撑域**（6 服务） | project / document / collab-ws / collab-persistence / notify / audit | 5% → 25% → 50% → 100% | 每阶段 20min | ~1h |
| **平台域**（4 服务） | auth / billing / gateway-bff / admin | 25% → 50% → 100% | 每阶段 10min | ~30min |

实施细则：

1. **CI 卡点**：Helm chart 模板加 `canary_strategy` 字段，按 `service_domain` 渲染不同阶段配置
2. **schema 校验**：proto/ 加枚举 `ServiceDomain`，CI 验证服务注册时 `service_domain` 字段不为空
3. **回滚阈值**：任一阶段 P99 恶化 > 20% 或错误率 > 1% 自动回滚到上一阶段
4. **跳过条件**：紧急 hotfix 允许跳过 canary，由 SRE Lead 一次性决策

### 4.5 影响

- **正面**：核心域风险得到更细控制，平台域部署效率提升
- **负面**：CI 配置复杂度增加，新人需理解 3 套 canary 规则
- **风险**：紧急 hotfix 跳过 canary 风险 → 必须由 SRE Lead 决策 + 强制 Postmortem

### 4.6 验证 / 关闭

- 关闭时点：M1-Sprint 1 末
- 验证动作：可热插拔部署设计书 §8.2 升 v1.1 + Helm chart 模板改造
- 签字方：运维

### 4.7 关联

- 上游：QA 登记册 v1.1 §2.3
- 关联 ADR：ADR-001（微服务架构，含服务域划分）
- 下游：`CATs_可热插拔部署与运维设计_v1.0` §8.2、`CATs_インシデント対応プレイブック_v1.0`（回滚流程）

## 5. QA-047 admin UI M1 上线模块

### 5.1 背景

运维设计书 §7.2 假设 M1 可上线 admin UI 5 模块（服务总览 / 部署 / 审计 / LLM 网关管理 / 协作会话监控）。但 M1 启动时 5 个模块同时交付的工程量与 UI 验证成本极高，存在 M1 即失败风险。

### 5.2 关心事项

QA 登记册 v1.1 §2.3：admin UI M1 上线模块 Open（架构+运维共识）。

### 5.3 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| A. **M1 = 3 模块** ✅ | 服务总览 / 部署 / 审计 | 聚焦核心，资源可控 | LLM 网关/协监 M2 才上 |
| B. M1 = 仅总览 | 只上 1 个 | 极简 | 部署/审计推迟，M1 完整性不足 |
| C. M1 = 5 模块全上 | 5 个全上 | 一步到位 | 工程量大，UI 验证不充分风险 |

### 5.4 决策

**采用 A：M1 上线 3 模块（服务总览 / 部署 / 审计）**。

| 模块 | M1-Sprint 0 | M1-Sprint 1 | M1-Sprint 2 | M2 |
|------|:-----------:|:-----------:|:-----------:|:--:|
| **服务总览** | 基础框架 + 服务列表 | 节点状态 + 资源指标 | 告警事件 | — |
| **部署** | Helm chart 触发 + 历史 | Canary 阶段控制（QA-046）| 回滚 + Diff | — |
| **审计** | 审计日志查询 | 审计保留期配置（QA-018）| 审计导出 CSV | — |
| LLM 网关管理 | — | — | 仅 API（管理 UI 推迟）| ✅ M2 |
| 协作会话监控 | — | — | — | ✅ M2 |

实施细则：

1. **admin UI Monorepo**：`apps/admin-ui/` 与 web 共享 Radix UI 组件库 + design token
2. **MVP 定义**：M1 末必须"可演示"3 模块 → SRE 演示场景：① 服务总览看 16 服务健康 ② 部署触发 canary 5 阶段 ③ 审计查 90 天日志
3. **可观测性埋点**：3 模块核心动作全埋点（点击 / 表单提交 / 错误），数据回流到 telemetry 服务
4. **吸收有道设计语言 4 原则**（详见 `CATs_UI-UX设计书_v1.1` §14 总览）：
   - **折叠屏适配**（§10）：admin UI 在折叠屏 / 大屏（≥ 1400 px）自动进入三栏布局（服务列表 / 详情 / 告警面板）
   - **动态主题**（§11）：支持 3 套主题（light / dark / 暖色护眼），任务感知策略（长任务自动暖色滤镜）
   - **WCAG AAA**（§12）：3 模块所有交互达到 AAA 标准，CI 强制 axe-core / pa11y-ci 卡点
   - **极简速度**（§13）：M1 末 3 模块 P99 LCP ≤ 1.0s；包体预算：Tauri ≤ 80MB / Web JS ≤ 200KB gzip

### 5.5 影响

- **正面**：M1 交付风险可控，UI 验证充分
- **负面**：LLM 网关管理员临时用 admin CLI + API 客户端
- **风险**：M2 推迟的 2 个模块若 M2 期间需求变化大需重做 → M1 末 LLM 网关 / 协监需求复核会

### 5.6 验证 / 关闭

- 关闭时点：M1-Sprint 0 末（admin UI Monorepo 脚手架 + 3 模块 Scaffolding 完成）
- 验证动作：admin UI Monorepo repo + Helm chart 整合 + SRE 演示场景过审
- 签字方：架构 + 运维

### 5.7 关联

- 上游：QA 登记册 v1.1 §2.3
- 关联 ADR：ADR-001（微服务架构）、ADR-004（前端栈 - React）
- 下游：`CATs_可热插拔部署与运维设计_v1.1` §7.2（WT-H4 已升 v1.1）、`CATs_UI-UX设计书_v1.1`（§10-§14 折叠屏/动态主题/WCAG AAA/极简速度）

## 6. QA-048 审计不可篡改实现

### 6.1 背景

审计日志合规要求"不可篡改"。PG 触发器阻断 UPDATE/DELETE 是最简实现，但仅靠单层防御不够：① trigger 可能被 super-user 误关 ② 备份恢复场景下历史日志会被覆盖 ③ 异地审计可证性不足。需要"深度防御"——多层保护 + 异地证据。

### 6.2 关心事项

QA 登记册 v1.1 §2.3：审计不可篡改实现 Open（合规+DBA）。

### 6.3 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| A. PG 触发器阻断 | 单一 trigger 阻断 UPDATE/DELETE | 简单 | 单点风险（trigger 误关、备份覆盖） |
| B. Kafka WORM topic | 异步复制到只读 Kafka | 异地证据 | 异步链路延迟，PG 写后 Kafka 失败窗口 |
| C. **触发器 + Kafka 双写** ✅ | 触发器快路径 + Debezium CDC 投递 Kafka WORM | 深度防御：快路径阻断 + 异地证据 | 复杂度中等，依赖 Debezium 链路 |

### 6.4 决策

**采用 C：PG 触发器 + Kafka WORM 双写**。

| 防线 | 实现 | 阻断/检测 | 失效场景 |
|------|------|----------|----------|
| **L1 快路径** | PG trigger `audit_log_no_modify`，对 `audit_log` 表阻断 `UPDATE/DELETE`（除 super-user） | 阻断 99% 误操作 | super-user 误关 trigger |
| **L2 异步证据** | Debezium CDC 监听 `audit_log` → 投递到 Kafka `audit-worm` topic（只读 + 7y 保留） | 异地证据 + 篡改可证 | Debezium 链路故障窗口（秒级） |
| **L3 周期校验** | SRE 每日 cron 对比 PG `audit_log` 与 Kafka `audit-worm` 记录数 | 告警链路断裂 | cron 失败未告警 |

实施细则：

1. **trigger 实施**：`audit_log_no_modify` 在 `audit_log` 表上 `BEFORE UPDATE OR DELETE` 抛异常
2. **CDC 配置**：Debezium connector 监听 `audit_log` 表，发布到 Kafka topic `audit-worm`
3. **Kafka 配置**：`audit-worm` topic 设置 `cleanup.policy=delete, retention.ms=220752000000`（7 年）
4. **每日校验**：SRE 脚本 `audit_consistency_check` 比对 PG count 与 Kafka count，差异 > 0 触发 P1 告警
5. **审计签名**（可选 M2）：考虑给 Kafka 消息加数字签名（HSM 或 Vault），进一步增强可证性

### 6.5 影响

- **正面**：满足等保 2.0 三级 + GDPR + enterprise 客户审计要求
- **负面**：Debezium 链路运维成本（已在 ADR-006 Outbox 共享基础设施）
- **风险**：Debezium 故障窗口期内的篡改无法被 L1 阻断 → L3 周期校验必须稳定

### 6.6 验证 / 关闭

- 关闭时点：M1-Sprint 1 末
- 验证动作：trigger 实施 + Debezium 部署 + Kafka topic 配置 + 校验脚本 + 故障注入测试
- 签字方：合规 + DBA
