## 1. 项目背景与目标（延续并更新 v0.1 §1）

CATs 定位从"团队内部工具"扩展为"可在客户局域网内私有化部署的多租户翻译 SaaS 平台"，目标仍是把传统 CAT 工具的多步流程压缩为「看到 → 选中 → 翻译 → 确认」的近乎两步操作，同时把可处理的媒体范围从纯网页文本扩展到音视频、PDF、Office 文档、动图与游戏本地化资源。

**成功标准（更新）：**
- 网页选区翻译单次操作链 ≤ 2 个显式动作（v0.1 已定标准，延续）。
- 常见句段（TM 命中）翻译即时、不调用云端 API（延续）。
- 术语库命中项译文 100% 符合规定术语（延续）。
- 敏感内容可在不出本地/不出局域网的前提下完成翻译（延续，架构设计书 §14 落地为 fail-closed 合规路由）。
- **新增**：单集群支持 50–3000 并发用户（架构设计书 §1.1 已定架构目标，本文档正式登记为需求）。
- **新增**：音视频/PDF/Office 类任务从提交到产出，P95 处理时长纳入 SLA 监控（具体阈值见 §6 非功能需求）。

## 2. 已锁定的架构约束（承接 v0.1 §2，标注变更）

| 编号 | v0.1 结论 | v2.0 现状 | 说明 |
|---|---|---|---|
| C1 部署形态 | 薄扩展 + 本地伴随引擎 | **变更**：Tauri 原生客户端 + Next.js 控制台 + K3s 微服务集群 | 见命名变更说明 §2 原因分析，v0.1 假设的"浏览器扩展承载重计算"在音视频/OCR/游戏引擎资源解析需求下已不成立 |
| C2 定位 | 团队内部工具，不做账号/计费/多租户 | **变更**：局域网私有化多租户 SaaS，需账号体系（`auth-service`/`user-service`）与订阅配额（`user_db.subscriptions`），但**不做对公网开放的商业化计费** | 仍不做"公网 SaaS 商业计费"，"多租户"特指同一局域网部署内的多组织隔离，非对外销售形态 |
| C3 数据合规 | AI Gateway 模型路由 + 合规开关 | 延续，落地为 `COMPLIANCE_BLOCKED` 错误码 + fail-closed（接口设计书 §1.4/§3.10） | 无变更 |
| C4 数据归属 | 本地 SQLite 权威 + 轻量中心同步 | **变更**：PostgreSQL 按服务逻辑库拆分为唯一权威存储，客户端本地 SQLite 降级为离线缓存/队列（模块设计书 §2.3），不再是"权威副本" | 因多租户协作场景下"本地为权威"不再成立，改为服务端权威、客户端离线缓存 |
| C5 多语种 | TM/术语主键含 `源语言→目标语言` | 延续，`translation_memory`/`terms` 表结构见数据库设计书 §4.3 | 无变更 |
| C6 存量数据 | 需清洗+映射+导入管道 | 延续，`worker-service` 承接批量导入（接口设计书 §3.9） | 无变更 |

## 4. 用户与典型场景（承接 v0.1 §4，扩展场景）

- **主要用户**：内部本地化译员/反馈处理人员（延续），新增**游戏本地化项目组**（策划/程序/QA 协同处理引擎工程内文案）、**组织管理员**（管理成员/配额/审计，新增角色）。
- **典型工作流（新增，游戏本地化场景）**：项目方在 CI 中执行标准引擎抽取（Unity Gather/Unreal GatherText/Godot 直接产出 .po）→ `cats-gameloc-cli` 上传抽取结果 → 系统按 TM/术语翻译 → 项目方拉取回写产物 → 执行引擎侧编译步骤（Unreal 场景需要）→ 提测阶段可选跑伪本地化/截图回归检查。详见游戏本地化模块设计书 §8。

## 6. 非功能需求（承接 v0.1 §6，补充 SaaS 化后的量化指标）

- **并发规模**：单集群支持 50–3000 并发用户（架构设计书 §1.1），需在验收测试中给出压测报告。
- **延迟分层**：延续 v0.1 L0~L3 分层定义。
- **媒体处理 SLA（新增，待与客户/PM 确认具体数值，暂列占位阈值供评审讨论）**：短音视频（<10 分钟）P95 端到端处理时长 ≤ 15 分钟；PDF（<50 页）P95 ≤ 5 分钟；具体阈值待 §9 O10 确认后转为正式验收标准。
- **合规**：延续 v0.1，fail-closed 已在接口层固化为 `COMPLIANCE_BLOCKED` 错误码。
- **离线可用**：延续 v0.1，客户端离线队列设计见模块设计书 §2.3。
- **数据安全**：PostgreSQL 各逻辑库独立账号最小权限（数据库设计书 §2），密钥经 SealedSecrets 管理（架构设计书 §14）。
- **私有化部署**：游戏本地化场景需支持"本地解析模式"（不上传原始工程文件，仅上传脱敏后的中间表示），游戏本地化模块设计书 §10.3。

## 7. 数据需求（承接 v0.1 §7，更新存储形态）

- 存储：PostgreSQL 8 个逻辑库（按服务边界拆分，数据库设计书 §1），SQLite 降级为客户端本地缓存（非权威）。
- 同步：服务间通过 Outbox+CDC（Debezium）异步事件驱动，替代 v0.1"轻量中心同步服务"设想（架构设计书 §7）。
- 导入：清洗+字段映射+去重管道延续，新增游戏本地化场景的增量抽取（按 `content_hash` 去重，游戏本地化模块设计书 §10.2）。

## 10. 里程碑（更新，承接 v0.1 M1-M5 并对齐当前架构落地阶段）

架构设计书 §16 已给出三阶段基础设施落地路线图（阶段一单机 K3s 验证 → 阶段二多节点 → 阶段三生产 HA），本文档在此基础上补充**需求侧功能里程碑**，与之并行推进而非顺序依赖：

1. **M1 — 核心 CAT 闭环迁移**：v0.1 F1-F10 在 Tauri 客户端上重新实现（不再是浏览器扩展），验证核心翻译体验未因架构转型退化。
2. **M2 — 多租户基础设施**：F12（账号/配额）、F14（审计/报表）落地，具备局域网内多组织隔离使用的最小条件。
3. **M3 — 全媒体处理**：音视频/PDF/Office/动图五大媒体域按接口设计书 §4 落地，含异步任务编排 F13。
4. **M4 — 游戏本地化试点**：按游戏本地化模块设计书 §11 分阶段建议，优先落地 Godot + Unity 文本模式（F15-F17）。
5. **M5 — 增强能力**：O7-O9 涉及的 Jira 模式、多模型投票评审、文档级实体记忆，待对应 Open Issue 澄清后补充详细设计再排期。
