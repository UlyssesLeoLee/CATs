## 0. 阅读指南

本书是测试设计阶段的整体规划文档（架构设计书 §21 仅承诺了模块/接口/数据库 3 个详细设计，未明确承诺测试设计；本书作为新增的测试维度设计存在）。**结构对齐 JIS X 0129-3:2013（ISO/IEC/IEEE 29119-3）测试設計書标准模板**，并补充 IPA/SEC 实践中常见的风险驱动测试、测试体制等要素。**不**包含具体测试用例的步骤与断言——具体测试用例在 `04-测试/测试用例/` 目录下按服务/模块分别维护，本书定义"测什么、怎么测、用什么测、达到什么标准算过"。

配套的 Excel 工作簿 `CATs_测试设计书_v1.0.xlsx` 包含可筛选/排序的测试项总表、需求追溯矩阵、V 字模型 × 测试类型矩阵、缺陷等级定义、风险登记册、覆盖率与缺陷注入率基线、文档模板与术语集。

## 1. 前言

### 1.1 目的

依据 JIS X 0129-1:2013（ソフトウェアテストの概念と定義）与 IPA/SEC ソフトウェア開発データ白書对测试设计文档的要求，在项目关系者（架构师 / 开发 / 测试 / 运维 / 产品 / 合规）之间就 **测试范围、测试策略、测试技法、测试级别、入口/出口准则、缺陷管理、风险驱动测试投入、追溯性** 达成共识。

- 作为后续测试实现（`04-测试/测试用例/`）、测试执行、缺陷跟踪的输入。
- 为 CI 流水线的"准入/准出门禁"提供判定标准（架构设计书 §15 CI/CD 章节的测试层落地）。
- 作为测试外包/合作单位的能力评估与招标依据（参考 JIS X 0129-2:2013 §5 テスト組織の要求）。

### 1.3 用语定义

| 术语 | 中文/英文 | 定义 |
|---|---|---|
| SUT | 被测对象 / System Under Test | 本项目指 CATs 全系统或某一微服务/客户端/平台组件的子集。 |
| 仕様ベースドテスト | 规格/规约驱动测试 / Specification-Based Test | 以需求规约/接口规约/设计规约等文档为依据的测试技法。 |
| 構造ベースドテスト | 结构驱动测试 / Structure-Based Test | 以代码/系统内部结构为依据的测试技法（白盒）。 |
| 経験ベースドテスト | 经验驱动测试 / Experience-Based Test | 基于测试人员的知识、经验、直觉进行的测试。 |
| 故障ベースドテスト | 故障驱动测试 / Fault-Based Test | 通过故意注入故障来验证系统韧性。 |
| 同値分割 | 等价类划分 / Equivalence Partitioning | 将输入域划分为等价类，从每个等价类选取代表值测试。 |
| 境界値分析 | 边界值分析 / Boundary Value Analysis | 测试等价类的边界值（最小/最大/刚跨边界）。 |
| デシジョンテーブル | 判定表 / Decision Table | 用表格表达多条件组合与对应动作的测试技法。 |
| 状態遷移テスト | 状态迁移测试 / State Transition Testing | 验证系统状态机的合法/非法迁移。 |
| ユースケーステスト | 用例测试 / Use Case Testing | 依据业务用例场景验证端到端业务流程。 |
| ペアワイズテスト | 全对组合测试 / Pairwise Testing | 用最小组合覆盖所有参数对的组合爆炸问题。 |
| ステートメントカバレッジ | 语句覆盖率 / Statement Coverage | 被执行的代码语句数 / 全部语句数。 |
| ブランチカバレッジ | 分支覆盖率 / Branch Coverage | 被执行的分支数 / 全部分支数。 |
| MC/DC | 修改条件/判定覆盖 / Modified Condition/Decision Coverage | 每个条件独立影响判定结果都被验证。 |
| エラー推測 | 错误推测 / Error Guessing | 基于经验预测可能错误并设计针对性测试。 |
| 探索的テスト | 探索性测试 / Exploratory Testing | 同时设计、执行、学习的测试方法。 |
| フォールト挿入 | 故障注入 / Fault Injection | 故意向系统注入故障验证韧性。 |
| ミューテーションテスト | 变异测试 / Mutation Testing | 通过修改代码产生变异体，验证测试用例的检出能力。 |
| リスクベースドテスト | 风险驱动测试 / Risk-Based Testing | 根据风险评估分配测试资源的策略。 |
| トレーサビリティ | 追溯性 / Traceability | 需求、测试项、测试用例、缺陷之间的可追踪关系。 |
| 入口/出口基準 | 入口/出口准则 / Entry/Exit Criteria | 各级测试开始/结束必须满足的条件。 |
| 欠陥密度 | 缺陷密度 / Defect Density | 千行代码的缺陷数。 |
| 欠陥除去率 | 缺陷去除率 / Defect Removal Efficiency | 测试发现的缺陷占全部缺陷的比例。 |
| 欠陥挿入率 | 缺陷注入率 / Fault Injection Rate | 故意注入的故障占总代码量的比例（用于验证测试有效性）。 |
| R | 严格/Restricted | JIS X 0129-1 中定义的能力等级（达到 100% 覆盖率）。 |
| Cr | 弱/Weak | JIS X 0129-1 中定义的能力等级（达到基本判定覆盖）。 |
| V 字モデル | V 字模型 / V-Model | 开发阶段与测试级别的对应关系模型。 |
| シフトレフト | 测试左移 / Shift-Left | 测试活动在开发早期介入的实践。 |
| Idempotency-Key | 幂等键 | 客户端为写操作生成的唯一键，24h 内服务端对相同键返回首次结果（接口设计书 §1.1）。 |
| fail-closed | 失败时安全关闭 | 敏感内容处理链路失败时**中止**而非降级到云端（架构设计书 §1.2 原则 3）。 |
| Outbox + CDC | Outbox 模式 + 变更数据捕获 | 业务写与事件发布在同一事务（架构设计书 §7），任何崩溃后 Debezium 能从 Outbox 补齐。 |
| DR 演练 | 灾备演练 / Disaster Recovery Drill | 模拟单组件/单节点故障验证恢复能力。 |
| Trace ID | 链路追踪标识 | OpenTelemetry 生成的全局唯一 ID，贯穿同步调用与异步 Kafka 消息。 |
| SLO | 服务质量目标 / Service Level Objective | 如"99.9% 的 L0 翻译请求在 100ms 内返回"。 |
| SBT | 规模/Build/测试 / Scale-Build-Test | 阶段性集成测试方式。 |

## 2. 测试方针

### 2.1 全体方针

| 方针 | 说明 | 承接 |
|---|---|---|
| 原则先行 | 架构设计书 §1.2 的「确定性优先 / 单一权威 / 合规 fail-closed / 异步优先不滥用 / 不过度设计」五项原则必须**各自有专项测试活动**验证，不能仅作为文档口号。 | 架构原则 1-5 |
| 风险驱动 | 测试投入与风险成正比，**不在低风险区域堆测试**（如 UI 像素级回归），**重点压测高风险区域**（Kafka 复制积压、CDC 漏单、敏感内容上云）。 | R-01~R-12 风险、§5 风险登记册 |
| 全栈可观测 | 同步 HTTP/gRPC + 异步 Kafka 消息必须用**同一 Trace ID** 串起来（架构设计书 §13.2），测试报告中的每条失败用例必须能定位到链路中具体节点。 | OTel 规范 |
| 自动化优先 | 单元/契约/接口/性能/合规测试**默认自动化**，仅 E2E 探索性测试、UX 评估、DR 演练允许人工主导。 | JIS X 0129-2 测试自动化 |
| 持续测试 | 测试作为 CI 流水线的强制门禁，**不是发布前才跑**；每条 PR 至少跑相关服务的单元 + 契约 + 集成测试，准入失败阻断合并。 | CI/CD |
| 测试左移 | 需求评审时测试负责人介入提出可测试性问题；架构评审时介入提出可观测性问题；接口设计时介入提出契约测试覆盖要求。 | JIS X 0129-2 シフトレフト |
| 测试数据隔离 | 测试数据库、测试 Kafka Topic、测试对象存储 bucket、测试 MinIO 与生产**完全物理隔离**，严禁共用。 | K3s Namespace 隔离 |

### 2.2 测试原则

依据 JIS X 0129-1 测试原则，补充项目特定原则：

| 编号 | 原则 | 说明 |
|---|---|---|
| P-01 | テストピラミッドの維持 | 测试金字塔不倒挂：单元 ≫ 集成 ≫ E2E，比例约 70% / 20% / 10%。倒挂视为架构坏味道。 |
| P-02 | 早期テスト | 越早发现缺陷，修复成本越低。需求与设计阶段即介入。 |
| P-03 | 欠陥のクラスタリング | 缺陷聚集（Pareto 分布）：少数模块集中了大部分缺陷。重点测试这些模块。 |
| P-04 | 殺虫剤のパラドックス回避 | 同一组测试反复执行后不再发现新缺陷。需定期评审与扩充测试用例集。 |
| P-05 | テストはコンテキスト次第 | 测试活动因项目语境（局域网 SaaS / 50-3000 并发）而异，不照搬业界默认。 |
| P-06 | テストの独立性と可重入性 | 每条测试不依赖其他用例的执行顺序/状态。 |
| P-07 | テストの独立検証 | 失败的测试必须能由独立人员（不仅是作者）复现。 |
| P-08 | 弱いテスト禁止 | 禁止"看似通过但其实没验证"的弱断言（如"响应 200" 而不校验响应体关键字段）。 |

### 2.3 测试目标

| 编号 | 目标 | 量化指标 |
|---|---|---|
| T-1 | 需求 F1-F11（MVP 范围）的功能/接口/数据流 100% 可测且全部通过 | 100% 测试项覆盖 + 0 阻塞级缺陷遗留 |

| T-3 | 双写一致性：业务写 + Outbox 写中间崩溃不丢事件 | 100 次故障注入零事件丢失 |
| T-4 | 延迟分层达标：L0 < 100ms (p95)、L1 < 300ms (p95)、L2 首字 < 1s (p95)、L3 < 10s (p95) | 性能测试用例 100% 达成 SLO |
| T-5 | 离线/网络抖动场景下用户操作不丢失 | 离线队列测试 0 丢失 0 重复 |
| T-6 | 测试本身可在 CI 中稳定运行（无 flaky） | Flaky 率 < 1%，失败用例 24h 内复现率 ≥ 95% |
| T-7 | 缺陷可定位：任意严重级缺陷平均定位时间 < 30 分钟 | 缺陷平均定位时间 < 30 min |
| T-8 | 缺陷注入率验证测试有效性：每个核心服务通过故意注入 5‰ 的缺陷验证测试用例能发现 90% 以上 | 缺陷注入率 5‰ + 测试发现率 ≥ 90% |
| T-9 | 单元覆盖率：Rust/Python ≥ 80%，TS ≥ 70%；分支覆盖率 ≥ 70% | 覆盖率基线全部达成（§10.4） |
| T-10 | 缺陷去除率：单元 + 集成阶段去除 ≥ 80% 的注入缺陷；系统测试去除 ≥ 15%；交付前 < 5% 残留 | 缺陷去除率阶段性达成 |

### 2.4 V 字模型与各级测试定位

依据 JIS X 0129-2 测试过程与 IPA/SEC 实践，采用 V 字模型定位各开发阶段与测试级别的对应关系：

```
   需求定義         ──→  受入テスト（验收测试）
     ↑
   システム要件定義 ──→  システムテスト（系统测试）
     ↑
   ソフトウェア要件定義 ──→  結合テスト（集成测试）
     ↑
   ソフトウェア詳細設計 ──→  単体テスト（单元测试）
     ↑
   ──────────────────────── 実装 ────────────────────────
```

| 开发阶段 | 文档 | 对应测试级别 | 测试重点 |
|---|---|---|---|
| 需求定义 | OFCAT 需求定义书 §5.2 (F1-F11) | 受入テスト（验收测试） | 业务价值达成、用户场景、KPI 验证 |
| 系统需求定义 | 架构设计书 §1-2、接口设计书 §3-4 | システムテスト（系统测试） | 端到端业务流、性能、可靠性、安全、合规 |
| 软件需求定义 | 模块设计书 §1-3、接口设计书 | 結合テスト（集成测试） | 服务间契约、数据流、状态机、Outbox+CDC |
| 详细设计 | 数据库设计书 §4、模块设计书 §4-5 | 単体テスト（单元测试） | 函数/方法/类、状态机迁移、纯算法 |

各测试级别在 V 字模型中验证前序对应阶段的规约是否被正确实现。**V 字模型左臂与右臂必须一一对应**，否则视为测试覆盖缺口。

## 3. 测试级别

### 3.1 单元测试（コンポーネントテスト / Unit Test）

| 项 | 内容 |
|---|---|
| 目的 | 验证单个函数/方法/类的逻辑正确性（V 字模型最右端）。 |
| 颗粒度 | 函数级；不含跨进程/跨网络调用。 |
| 工具 | Rust: `cargo test` + `cargo-tarpaulin`（覆盖率）<br>Python: `pytest` + `pytest-cov`（覆盖率）<br>TypeScript（Svelte/Next.js）: `vitest` + `@vitest/coverage-v8`（覆盖率） |
| 技法 | ステートメントカバレッジ（语句覆盖）/ ブランチカバレッジ（分支覆盖）/ MC/DC（关键判定）。领域层强依赖 MC/DC（因含状态机迁移）。 |
| 范围约束 | 模块设计书 §1.1「领域层不得依赖 Web 框架类型」原则的落地保障——领域层可单测，API 层/基础设施层不强求单测（用契约/集成测试覆盖）。 |
| 重点覆盖 | 状态机迁移、TM 匹配算法（RapidFuzz/bge-m3）、术语强制校验、标签占位符保护、Outbox 写入唯一性约束。 |
| 入口准则 | 代码已实现并通过编译/Runtime check；Mock 与测试数据已就绪。 |
| 出口准则 | 单测失败数 = 0；覆盖率不低于 §10.4 基线；缺陷注入率达 §10.5 基线。 |

### 3.2 集成测试（結合テスト / Integration Test）

| 项 | 内容 |
|---|---|
| 目的 | 验证一个微服务与其依赖（数据库 / Kafka / 下游服务 stub）的协作正确性。 |
| 颗粒度 | 服务级，含真实数据库（测试库）/Kafka Topic/对象存储的本地实例或测试容器。 |
| 工具 | `testcontainers-python` 或 `testcontainers-rust` 起 PostgreSQL/Redis/Kafka 容器；Next.js 用 `next/jest` + `msw` mock 后端。 |
| 技法 | 契约测试（接口契约 / Schema 演进）/ 状态迁移测试（服务内状态机）/ 数据流测试（Outbox+CDC 链路）。 |
| 范围 | 仓储层真实 SQL 执行、Outbox→CDC→Kafka 真实链路（用 Debezium embedded 模式或测试用 PostgreSQL 实例）、Webhook/REST/gRPC 端点。 |
| 重点覆盖 | 双写一致性（业务表 + Outbox 表同事务）、Kafka 消费幂等、数据库迁移脚本（Forward + Rollback）、状态机非法迁移拒绝。 |
| 入口准则 | 服务能成功启动到测试环境，所有外部依赖可连接；单测已通过。 |
| 出口准则 | 所有集成测试通过 + 测试数据库与 Topic 在测试结束自动清理 + 契约双向一致。 |

### 3.3 系统测试（システムテスト / System Test）

| 项 | 内容 |
|---|---|
| 目的 | 验证完整系统的端到端功能、性能、可靠性、安全、合规。 |
| 颗粒度 | 跨服务、跨中间件、模拟真实用户场景。 |
| 工具 | `k6`（HTTP/WS 压测）+ `ghz`（gRPC 基准）+ `wrk2`（高精度延迟）+ `tauri-driver`（Tauri WebDriver）+ `playwright`（Web 控制台）+ 部署到 K3s `cats-test` Namespace 的 pytest 集成测试套件。 |
| 技法 | ユースケーステスト（用例测试）/ E2E（端到端）/ 性能测试（負荷/ストレス/容量）/ 故障注入（フォールト挿入）/ 探索的テスト（探索性）。 |
| 范围 | 12 个核心 E2E 场景（含视频/音频/PDF/Office/GIF/WebP/动图/离线恢复/合规敏感）；8 个故障注入场景；性能基线压测。 |
| 入口准则 | K3s 测试集群已部署完整版本（含 Harbor 镜像、Tempo/Loki 已启动）；集成测试已通过。 |
| 出口准则 | 12 个核心 E2E 场景全部通过 + 含 1 轮「网络分区」「服务重启」「Kafka 短暂不可用」故障注入场景 + 全部 SLO 达成。 |

### 3.4 验收测试（受入テスト / Acceptance Test）

| 项 | 内容 |
|---|---|
| 目的 | 验证系统满足业务需求与用户期望，由产品/需求方/最终用户代表主导。 |
| 颗粒度 | 业务场景级 + 效果指标达成。 |
| 工具 | 产品方主导的 UAT（手工/半自动）+ 需求方对 F1-F11 业务规则达成度的逐项确认。 |
| 技法 | 受け入れシナリオテスト（UAT 场景测试）/ KPI 达成度验证 / 探索的テスト。 |
| 范围 | OFCAT 需求定义书 §2.4 期望效果（KPI 候选）全部验证：<br>效果1：网页选区翻译的显式操作数 ≤ 2<br>效果2：TM 精确匹配即时且不调用云端 API<br>效果3：术语库命中项的译文术语符合率 100%<br>效果4：敏感内容上云率 0%<br>效果5：综合作业效率对比传统 CAT 3-10 倍 |
| 入口准则 | 系统测试已通过；产品方/需求方已就位；UAT 场景已冻结。 |
| 出口准则 | 产品/需求方签字 + UAT 场景全部通过 + 效果指标达成。 |

### 3.5 各级别入口/出口准则总览

| 级别 | 入口 | 出口 |
|---|---|---|
| 单元测试 | 代码已实现 + Mock 就绪 | 失败数 = 0 + 覆盖率达基线 + 缺陷注入率达基线 |
| 集成测试 | 单元测试已通过 + 外部依赖可连 | 全部通过 + 双写一致 + 契约双向一致 |
| 系统测试 | 集成测试已通过 + K3s 测试集群就绪 | E2E 12 场景全过 + 故障注入全过 + SLO 达成 |
| 验收测试 | 系统测试已通过 + 产品/需求方就位 | UAT 场景全过 + 效果指标达成 + 签字 |

## 4. 测试类型与测试技法

依据 JIS X 0129-4:2016 测试技法分类（仕様ベースド / 構造ベースド / 経験ベースド / 故障ベースド），结合 ISO/IEC 25010 质量属性（功能/性能/兼容/可用/可靠/安全/维护/移植）组织测试类型。

### 4.1 機能テスト（功能测试）

| 技法 | 中文 | 适用范围 | 关键应用 |
|---|---|---|---|
| 同値分割 | 等价类划分 | 输入域按等价类划分，每个等价类选代表值 | 邮件格式、文件大小、BCP-47 语言代码、页码范围等 |
| 境界値分析 | 边界值分析 | 等价类边界（最小/最大/刚跨边界） | Kafka 消息大小（< 1MB）、JWT 有效期、文件上传大小、分页参数 |
| デシジョンテーブル | 判定表 | 多条件组合与对应动作 | 翻译路径选择（TM 命中 / 命中 + 模糊 / 未命中 / 命中 + 合规敏感） |
| 状態遷移テスト | 状态迁移测试 | 状态机合法/非法迁移 | 任务状态机（queued→ingesting→processing→rendering→completed）、Session 状态机 |
| ユースケーステスト | 用例测试 | 业务用例场景 | 12 个核心 E2E 场景 |
| ペアワイズテスト | 全对组合测试 | 参数组合爆炸 | 翻译参数（源/目标语言 × 模型 × 领域 × 合规策略） |

### 4.2 構造テスト（结构测试 / 白盒测试）

| 技法 | 中文 | 覆盖率目标 | 关键应用 |
|---|---|---|---|
| ステートメントカバレッジ | 语句覆盖 | Rust/Python ≥ 80% / TS ≥ 70% | 所有可执行语句至少执行一次 |
| ブランチカバレッジ | 分支覆盖 | ≥ 70% | 所有判定（if/else、case）的每个分支至少执行一次 |
| コンディションカバレッジ | 条件覆盖 | ≥ 60% | 复合判定中每个子条件至少各取一次真假 |
| MC/DC | 修改条件/判定覆盖 | 关键判定 ≥ 80% | 状态机迁移、合规判定、安全相关判定 |

JIS X 0129-1 能力等级对应（参考）：
- **R（严格）**：100% 覆盖。
- **Cr（弱）**：基本判定覆盖。
- **本项目基线**：MC/DC 关键判定 ≥ 80%（R 与 Cr 之间的中间档）。

### 4.3 経験ベースドテスト（经验驱动测试）

| 技法 | 中文 | 适用范围 |
|---|---|---|
| エラー推測 | 错误推测 | 基于历史 bug 数据 + 开发者直觉；适用于边界条件、并发、空值等 |
| 探索的テスト | 探索性测试 | 时间盒（time-boxed）会议形式；用于发现新缺陷模式；由领域专家执行 |
| チェックリストベースド | 检查表驱动 | 基于 IPA セキュリティ要件チェックリスト、OWASP ASVS 等检查表 |

### 4.4 故障ベースドテスト（故障驱动测试）

| 技法 | 中文 | 适用范围 |
|---|---|---|
| フォールト挿入 | 故障注入 | K8s Pod kill / network partition / Kafka broker down / DB failover（见 §6 风险驱动测试） |
| ミューテーションテスト | 变异测试 | 验证测试用例的有效性（指标：变异得分 ≥ 80%）；可选用工具：`mutmut`（Python）、`cargo-mutants`（Rust） |

### 4.5 性能テスト（性能测试）

依据 IPA 非機能要求グレード（响应时间 / 吞吐量级别划分）：

| 子类型 | 目的 | SLO 目标（初版，待 PRE 校准） |
|---|---|---|
| 負荷テスト（负荷测试） | 验证在预期负载下的响应能力 | 并发 500 用户时核心服务错误率 < 0.1% |
| ストレステスト（压力测试） | 验证超出预期负载的极限与恢复能力 | 1000 用户时错误率 < 1%；超出后系统降级而非崩溃 |
| 容量テスト（容量测试） | 验证大数据量下的处理能力 | 单任务：30min 1080p 视频 < 5min；200 页 PDF < 2min；50 帧 GIF < 30s |
| スパイクテスト（尖峰测试） | 验证突发流量的应对 | 瞬时并发翻倍不导致系统雪崩 |
| ソークテスト（浸泡测试） | 验证长时间运行的稳定性 | 24h 持续运行无内存泄漏/性能下降 |

**延迟分层 SLO（来自需求 §6.2）：**

| 层级 | 条件 | 目标延迟 | 路径 |
|---|---|---|---|
| L0 | TM 精确匹配 | 即时·不调用 API（< 100ms p95） | 直接填充 |
| L1 | TM 模糊匹配 | 即时（< 300ms p95） | 填充+等待确认 |
| L2 | TM 未命中（默认） | ~1s 首字（< 1s p95） | 单模型+术语注入+QA |
| L3 | 用户指定 | < 10s 完成 | 多模型投票+评审 |

### 4.6 信頼性テスト（可靠性测试）

| 子类型 | 目的 |
|---|---|
| HA テスト（高可用测试） | 单节点/进程/副本故障的业务不中断或分钟级自愈 |
| DR テスト（灾备测试） | 整体基础设施损毁时的恢复能力（冷 DR：异地备份可搬迁恢复） |
| 観測性テスト（可观测性测试） | 指标/日志/链路追踪的正确性、完整性、可消费性 |

### 4.7 セキュリティテスト（安全测试）

依据 OWASP ASVS 4.0 + CWE/SANS Top 25 + IPA セキュリティ要件チェックリスト：

| 子类型 | 工具 | 频率 |
|---|---|---|
| SAST（静态应用安全测试） | `semgrep`（Python/Rust/TS）/ `bandit`（Python）/ `cargo-audit`（Rust crates 漏洞） | PR 门禁 |
| DAST（动态应用安全测试） | OWASP ZAP baseline scan | 每周 |
| SBOM（软件物料清单） | `syft` + `grype`（CI 中生成 SBOM 并阻断已知严重漏洞） | PR 门禁 |
| 密钥扫描 | `gitleaks`（历史提交 + 当前工作区） | PR 门禁 |
| 依赖漏洞 | `dependabot` + 每周 `pip-audit`/`cargo audit`/`npm audit` | 每周 |
| 渗透测试 | 第三方年度渗透（合规要求） | 年度 |

**专项安全测试场景：**
- 鉴权绕过：未带 JWT 401、过期 JWT 401、伪造签名 401、跨租户访问 403
- 越权访问：横向（org A 用户访问 org B 数据）/ 垂直（普通用户访问 platform_admin）
- 注入攻击：SQL 注入、命令注入、SSRF
- Web 攻击：XSS（仅控制台面）、CSRF（仅控制台面）
- 敏感信息泄露：日志/响应/异常信息
- JWT 签名攻击：算法替换攻击（RS256 → HS256）、重放攻击
- `Idempotency-Key` 滥用：高频重复键的存储资源耗尽
- OIDC 流程安全：state 参数、PKCE

### 4.8 互換性テスト（兼容性测试）

| 维度 | 范围 |
|---|---|
| 客户端 OS | Tauri：Windows 10/11、macOS 12+ (M1+Intel)、Ubuntu 22.04 LTS / Fedora 最新稳定版 |
| 浏览器 | Web 控制台：Chrome / Edge / Firefox 最新稳定 + 前一 LTS |
| 数据库 | PostgreSQL 18.6（见 [CATs_技术基线_v1.0 §1](../../02-基础设计/技术选型/CATs_技术基线_v1.0.md)） |
| Kafka | 3.x+（KRaft） |
| K3s | 1.x+（具体版本以 Argo CD 锁定为准） |

### 4.9 コンプライアンステスト（合规测试）

严格按架构设计书 §1.2 原则 3「合规 fail-closed」专项测试：

- 敏感项目（`project.force_local_model=true`）调用云端模型 → 阻断
- 敏感项目本地模型不可达 → 返回 `COMPLIANCE_BLOCKED`，不降级
- 敏感内容载荷在 HTTP/gRPC 抓包中**不可出现**（出本机/集群即失败，使用 `mitmproxy`）
- 审计日志完整记录所有敏感操作（术语变更、策略变更、敏感项目访问）
- 数据导出/导入受敏感策略约束
- 法規遵循：个人隐私法（GDPR/PIPL）、行业规范（游戏本地化的文化敏感性等）

## 5. 风险驱动测试（リスクベースドテスト）

依据 JIS X 0129-2 测试过程与 IPA/SEC 实践，对架构设计书 R-01~R-12 风险与项目级风险进行评估，按风险等级分配测试投入。

### 5.1 风险评估方法

采用 **风险矩阵**（可能性 × 影响）评估每条风险：

| 等级 | 名称 | 定义 | 测试投入 |
|---|---|---|---|
| 高 | 高风险 | 影响核心业务或数据完整性 | 100% 测试覆盖 + 故障注入演练 |
| 中 | 中风险 | 影响次要功能或可通过 workaround 缓解 | 70% 测试覆盖 |
| 低 | 低风险 | 不影响核心功能或仅有轻微体验问题 | 30% 测试覆盖 + 监控告警即可 |

### 5.2 风险登记册（项目级）

完整列表见 `CATs_测试设计书_v1.0.xlsx` 的「风险与缓解」工作表。本节为索引性总览：

### 5.3 故障注入场景（テストレベル：システムテスト）

| 场景 | 工具 | 验证内容 |
|---|---|---|
| ① 单微服务 Pod 重启 | `kubectl delete pod` | 任务从中断点继续推进 |
| ② Kafka broker 短暂不可用（< 5min） | 手动 stop broker | 事件最终一致送达，不丢 |
| ③ Debezium connector 重启 | `kubectl delete pod` | 复制槽位置不丢失，继续从 LSN 推进 |
| ④ PostgreSQL 主节点宕机 | 手动 `pg_ctl stop` | 自动 failover，业务中断时长符合 SLO |
| ⑤ 客户端断网 | `tc netem` 注入丢包 | 离线队列累计，恢复后自动重放且无重复 |
| ⑥ 本地 LLM 不可达（合规项目） | 模拟本地模型宕机 | 翻译 fail-closed，错误码 `COMPLIANCE_BLOCKED` |
| ⑦ K3s 控制面 1/3 节点宕机 | 手动 stop etcd | 集群仍可调度 |
| ⑧ Harbor 不可用 | 模拟 Harbor 宕机 | 已运行 Pod 不受影响，新调度受影响 |

### 10.2 自动化范围

**自动化（默认）**: 单元/契约/接口/性能/合规/数据一致性/故障注入/缺陷注入率验证。

**半自动**: E2E 探索性部分（人 + 自动脚本协作）。

**手动**: 验收测试、UX 评估、DR 演练、人工审查类活动（代码评审、设计评审）。

### 10.3 CI/CD 集成

| **Pre-commit** | `git commit` | `pre-commit` 钩子：gitleaks / 格式化 / 简单 lint |

### 10.5 缺陷注入率（欠陥挿入率）

依据 JIS X 0129-2 与 IPA/SEC 实践，通过故意在代码中注入已知缺陷，验证测试用例的发现能力：

| 服务 | 缺陷注入率 | 测试发现率目标 |
|---|---|---|
| 核心服务（auth/task/translation-core/project/audit） | 5‰（每 200 行注入 1 个缺陷） | ≥ 90% |
| 一般服务 | 3‰（每 333 行注入 1 个缺陷） | ≥ 80% |
| 客户端 | 2‰ | ≥ 70% |

**实施方式**：
- 选定代表性模块，使用变异测试工具（`mutmut` / `cargo-mutants`）自动生成变异体
- 统计被现有测试套件检出（杀死）的变异体比例 = 变异得分
- 变异得分 ≥ 缺陷发现率目标

**频次**: 每里程碑 + 每次大重构后。

### 10.6 缺陷去除率（欠陥除去率）

## 12. 缺陷管理

### 12.1 缺陷生命周期

```
[发现] 新建 → 分配 → 修复中 → 待验证 → 验证通过/打回 → 关闭
                                ↓                ↓
                            暂缓（产品决策）    重新打开
```

### 12.2 缺陷等级

| 等级 | 名称 | 定义 | 示例 | 修复 SLA |
|---|---|---|---|---|
| **P0** | 阻断级（致命） | 核心功能不可用 / 数据丢失 / 安全漏洞 | TM 匹配崩溃、合规内容上云、PG 主从数据不一致、用户登录全挂 | 24h |
| **P1** | 严重级 | 主要功能不可用但有 workaround | 某媒体类型翻译链路全断、性能 SLO 偏差 > 50% | 3d |
| **P2** | 一般级 | 次要功能异常 | 单个 endpoint 报错、UI 在某浏览器某页错位、告警文案不准确 | 2w |
| **P3** | 轻微级 | 体验/文案问题 | 提示文案不通顺、图标错误、文档错误 | 下迭代 |
| **P4** | 建议级 | 优化建议 | 性能可优化点、可读性 | 评估 |

### 12.3 度量指标

| 指标 | 计算方式 | 目标 |
|---|---|---|
| 缺陷密度（欠陥密度） | 缺陷数 / 千行代码 | < 1.0（按服务） |
| 缺陷去除率（欠陥除去率） | 各阶段发现的缺陷数 / 总注入缺陷数 | 阶段目标见 §10.6 |
| 缺陷逃逸率 | 测试通过后线上发现的缺陷 / 总缺陷 | < 5% |
| P0 缺陷遗留 | 当前未关闭的 P0 数 | = 0 |
| 平均修复时长 | 缺陷从新建到关闭的平均时长 | P0 < 1d / P1 < 3d / P2 < 14d |
| 重打开率 | 重打开缺陷数 / 总关闭缺陷数 | < 10% |
| 测试用例执行率 | 已执行用例 / 总用例 | 100%（出口准则） |
| 测试通过率 | 通过用例 / 已执行用例 | > 95%（其余为已知缺陷/暂缓） |
| 缺陷注入率验证 | 故意注入的缺陷被发现的比例 | 见 §10.5 |
| 缺陷平均定位时间 | 缺陷从发现到定位根因的平均时长 | < 30 min（目标 T-7） |
