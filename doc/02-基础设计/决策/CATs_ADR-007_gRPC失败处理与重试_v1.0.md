# CATs ADR-007：gRPC 失败处理与重试策略

> **文档编号**：CATs-ADR-007
> **版本**：v1.0
> **创建日**：2026-08-26
> **作者**：架构师(worker 代签 per DEC-008)
> **状态**：已接受

## 1. 背景

ADR-002 已落定服务间同步通信走 gRPC(proto3)+ Kafka 异步。但 gRPC 调用在生产中必然面对三类失败：

- **瞬时失败**：网络抖动、对端重启、连接池耗尽 → 重试可恢复
- **持续失败**：对端服务降级、依赖链雪崩 → 需熔断隔离
- **业务失败**：参数非法、状态冲突 → 不可重试，需快速失败

CATs 15 服务 + 4 共享库的调用关系中，关键路径存在跨 3-5 服务的依赖链(如 llm-gateway → translate-orchestrator → tm / term / qa-engine)。若无统一失败处理策略，任意下游抖动都会沿调用链放大，导致整体可用性崩塌。

QA-015 已登记为 Open 项，要求给出 gRPC 失败处理与重试的明确策略。L-7 风险登记册中"分布式调用可靠性"对应此 ADR。

要决策的核心问题：

- **重试粒度**：哪些错误码重试、重试几次、退避策略?
- **熔断阈值**：何时熔断、半开探测条件?
- **降级策略**：关键业务 vs 非关键业务在持续失败时如何降级?
- **是否引入 Saga 编排器**：跨多服务的长事务(典型如 translation 任务)需不需要 Saga?

## 2. 选项

| 选项 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| **A. 标准重试 + 熔断 + 死信队列** ✅ | 指数退避重试、gRPC status code 白名单、熔断器、关键业务落 DLQ | 实现成本可控、与 ADR-002 共享库 `common-grpc` 自然集成、SRE 团队已熟悉 Hystrix/Resilience4j 范式 | 业务需自己标注"关键 vs 非关键"，需规范约束 |
| **B. 全异步化** | 所有 gRPC 调用改为 Kafka 异步事件 | 调用方解耦到底 | 同步查询场景(翻译结果回查、TM 检索)不适用；引入 1 跳延迟，与"流式翻译低延迟"目标冲突 |
| **C. Saga 编排** | 引入 Temporal / Camunda 编排长事务 | 自动补偿、可视化 | 增加重量级中间件、SRE 团队无运维经验、对绝大多数短事务过设计 |

补充说明：

- 选项 A 的"标准重试"指 grpc-go / tonic 内置 retry policy + 自研熔断器，不引入新中间件
- 选项 C 即使对 translation 长任务也过设计——translation 断点续传由业务状态机承担(见 ADR-006 §3.2)，不需 Saga 编排

## 3. 决策

**采用 A：标准重试 + 熔断 + 死信队列(关键业务)；非关键业务降级到缓存 / 默认值；不引入 Saga 编排。**

实施细则：

1. **重试策略**(由 `common-grpc` 拦截器统一注入)
   - 仅对 gRPC status code `UNAVAILABLE` / `DEADLINE_EXCEEDED` / `RESOURCE_EXHAUSTED` 重试
   - 默认重试 3 次，指数退避(基线 100ms，倍数 2)，最大间隔 2s，加入 ±20% 抖动
   - 幂等性要求：仅 `GET` 类查询与声明 `idempotent=true` 的 RPC 可重试；写操作由调用方负责幂等(去重表 / 业务主键)
2. **熔断策略**
   - 滑动窗口 10s，错误率 > 50% 触发熔断，熔断持续 30s
   - 半开状态：放行 1 个探测请求，成功则关闭，失败则再次熔断
   - 熔断器状态暴露 Prometheus 指标 `grpc_circuit_breaker_state{service="..."}`
3. **死信队列(DLQ)**
   - 关键业务(翻译任务提交、文档保存、计费)落 DLQ 主题 `cats.dlq.critical.v1`，含完整请求上下文 + 失败原因
   - DLQ 由 admin 域消费，写入 `audit` 表告警 + 飞书通知
4. **降级策略**
   - **关键业务**：失败即拒绝，返回明确错误码(用户可感知)
   - **非关键业务**(TM 检索建议、术语高亮、推荐)：失败即返回缓存值 / 默认空集 / 默认占位
5. **Saga 不引入**
   - translation 任务状态由 translate-orchestrator 自管(参见 ADR-006 §3.2)
   - 跨服务补偿由各服务的 outbox 事件反向触发，不引入统一编排器

## 4. 影响

- **正面**：
  - 与 ADR-002 共享库分层天然契合，零新中间件
  - SRE 团队已具备 Hystrix/Resilience4j 经验，无学习成本
  - 熔断指标接入可观测性平台(参见 ADR-002 下游关联)
  - 关键业务 DLQ 兜底，避免"静默丢任务"
- **负面**：
  - 业务需在 proto 注解中声明 `idempotent` → 需 buf lint 规则强制
  - 重试 + 熔断调试链路略复杂(单次用户请求最多重试 3 次 = 4 次下游调用)，需 trace 全链路关联
  - DLQ 主题运维需定期巡检(已在 53 任务规划)
- **风险**：
  - 写操作未正确声明幂等 → 重复执行业务副作用 → 必须在 M1 评审会上把"幂等性声明"列入 DoD
  - 熔断阈值(50% / 10s)是否合理需 M2 压测校准 → 写入压测任务清单
  - 跨域长事务无 Saga 兜底 → 极端场景(如计费半成功)需人工介入 → admin 域需值班 runbook
